# 固定桥接 API 契约，由服务端适配部署 SDK

当前 qmt-rpyc 的业务接口由部署 SDK 动态发现，输入与返回结构可能随 SDK 升级变化；只固定传输协议或保存签名快照不足以稳定客户端行为。用户于 2026-09-23 确认采用独立的桥接 API 契约与服务端适配层，基于当前版本建立首个契约，未来 SDK 差异由服务端吸收，并允许为了引入契约机制统一升级一次客户端。

契约范围以 a-trader、a-options 的实际依赖为优先，补充明确选定的股票分析能力；不要求全量导出 SDK。相比仅检查接口快照，此方案承担返回模型与适配验证的成本；相比重新设计一套业务 API，它以当前接口作为基线。返回值只包含契约约定字段；若导出回调接口，回调由桥接层统一管理。

用户进一步确认保留现有返回容器与字段名，并在其中定义稳定的字段模型。时间逐字段固定现有格式，未来 SDK 变化由服务端适配；保留委托秒、交易日毫秒等已有差异，以避免为统一单位而额外改变使用方的对账和日期处理。期权列表保留当前 SDK 的日期参数含义，由使用方继续按实际到期日筛选；下载任务成功仅表示 SDK 下载调用正常结束，不承诺请求数据完整。

用户另外明确要求补入撤单能力。V1 选入按委托编号和按市场/柜台合同编号的两个同步撤单接口，最终委托状态通过已有委托查询确认；不因此扩展为完整异步交易回调 API。

首版 K 线周期限定为 `1m/5m/15m/30m/1h/1d`。用户确认当前部署 SDK 不支持周线、月线，需要自行计算，因此将周/月聚合留给使用方，本次桥接层不承担生成这些数据的职责；也不自动提供 `60m` 别名。选入范围仍需完成对应查询和下载的验证，范围确认不等同于验证已完成。

发现签名不一致不得阻止服务启动：服务端输出警告，调用受影响接口时返回明确错误。保留使用方必需接口与运行时拒绝不兼容调用是不同约定：前者要求补齐这些接口的契约和适配，后者防止 SDK 漂移被静默传给使用方。

同一契约版本必须支持多种 MiniQMT SDK。实现采用策略、注册表与工厂：按公开接口独立选择显式 SDK 适配器，允许多个策略面向同一个 V1。兼容性探针检查各策略依赖，不把包版本或整个 SDK 指纹当作唯一选择条件。新增适配器不修改 V1，优先级歧义按不可用处理。

首个基线适配器与多策略机制已实现；dev2 已在 Windows 完成只读联调，尚未发布。实现和验收边界见[实现记录](../design/contract-v1-implementation.md)及[dev2 兼容性修复记录](../design/dev2-compatibility-fix.md)。实际部署清单来自 [qmt-api-baseline-20260923.json](../api/qmt-api-baseline-20260923.json)，使用方证据见[依赖调查](../api/consumer-dependencies.md)，具体范围和待验证项见[设计记录](../design/stable-api-contract.md)。
