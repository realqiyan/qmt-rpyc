# 本机软件升级命令

本文记录已确认并实施的 `qmt-rpyc-server update` 与 `qmt-rpyc-client update` 设计。架构选择见 [ADR 0006](../adr/0006-local-update-and-process-management.md)。

## 已确认的边界

- 两个命令都在运行命令的现有 Python 环境中升级 `qmt-rpyc`，延续原环境升级方式。
- 每个命令只升级本机环境，不通过客户端升级远端服务器。
- 本次不引入独立版本环境及版本切换式升级。
- 默认升级到最新稳定版，保留 `--pre` 选择预发布版本，增加 `--version <版本>` 指定目标版本。
- 默认允许跨 MINOR 升级，并提示客户端、服务端和 BigQMT 策略的配套要求。
- 服务端采用当前用户的后台进程管理，提供启动、停止、状态与重启能力；本期不引入 Windows 系统服务、开机自启或崩溃自动拉起。
- `start` 默认后台运行，保留 `--foreground` 用于调试，增加 `stop`、`restart`；`status` 在 RPC 不可用时也能报告进程状态。
- 一个 Python 环境只管理一个服务实例；多实例使用不同虚拟环境，重启沿用启动时的配置。
- 升级不启动服务：原本运行则停止后升级，原本停止则只升级；安装验证后输出推荐的下一步命令，由用户决定何时启动。没有需要安装的版本变化时不停止服务。
- 停机先拒绝新业务请求，等待在途请求与下载任务完成，默认等待 60 秒；超时取消升级并恢复接收请求，不默认强杀。
- 检测到 editable 安装时拒绝升级，并提示通过 Git 更新源码；普通安装和托管安装支持 `update`。
- 两个命令都通过新进程验证安装版本及相应命令能够正常加载；升级成功不要求启动服务或 RPC 就绪，QMT 暂时断线不算升级失败。
- 安装或安装后验证失败时明确报告失败阶段并提供修复指引；本期不自动回滚，也不自动重试交易请求。
- 删除被新命令替代的启动包装脚本，将安装脚本收敛为一个仅负责首次安装的入口；后续使用 `init/start/update`。保留开发用的 `scripts/setup.bat`、`scripts/setup.sh`，同步清理文档及发布包引用。
- 默认稳定版从官方 PyPI 获取；`--pre` 或显式指定预发布版本时从官方 TestPyPI 获取目标包，第三方依赖从官方 PyPI 获取，不增加仓库选择参数。显式指定稳定版本时以该精确版本及其稳定来源为准。
- 允许显式 `--version <旧版本>` 降级；默认升级不自动降级。不因目标旧版本缺少后台管理能力而拒绝安装；执行后输出适用于目标版本的下一步命令，不自动启动。
- 在服务端环境执行 `qmt-rpyc-client update` 时，识别该环境的服务实例并共用服务端升级流程；同样等待在途工作结束、停止服务、升级和验证，最后输出下一步命令。普通客户端环境只执行包升级和验证。

## 迁移与兼容约束

- 旧服务端的 `update` 在原进程中检查升级结果；新实现由两端共用流程，通过新进程验证安装，并保留服务端依赖。
- 两个命令属于同一个 Python 发行包；同一环境内升级该包会同时更新两个命令。
- 旧版本前台进程没有本机管理通道，首次迁移前须手动停止；新管理命令不接管无法确认归属的旧进程。
- 源码 setup 使用 editable 安装，发布包升级与源码工作区更新需要区分。
- BigQMT 策略需在 QMT 中另行替换、启动；安装 Python 包不等于策略已更新。配套版本要求见[版本与构建标识](../versioning.md)。
- 原 `start-bigqmt.bat` 的适配器选择职责改由 `init --adapter bigqmt` 持久化到配置；后台启动及显式重启保留实际运行配置。
- 旧 Release ZIP 的启动包装脚本会验证其旁边的策略文件，升级后可能因旧策略版本而拒绝启动。新管理命令的安装验证不能依赖旧 ZIP 附带文件。
- 发布流程、开发 setup 提示、Windows 验收包生成器及相关测试已同步调整。独立验收包保留自己的前台调试入口。

## 命令行为

| 命令 | 行为 |
| --- | --- |
| `qmt-rpyc-client update` | 升级本机当前环境中的包；若存在该环境的服务实例，协调停机 |
| `qmt-rpyc-server update` | 协调本环境停机并升级包，保留服务端依赖 |
| `update --pre` | 从官方 TestPyPI 选择预发布渠道的目标版本 |
| `update --version <版本>` | 安装精确版本，允许降级，包括不支持新后台管理机制的旧版本 |
| `qmt-rpyc-server start` | 在当前用户下后台启动，启动成功需确认 RPC 就绪 |
| `qmt-rpyc-server start --foreground` | 前台运行，供调试使用 |
| `qmt-rpyc-server stop` | 停止接收新业务请求，等待在途工作完成后退出 |
| `qmt-rpyc-server restart` | 显式停止并按原配置重新启动 |
| `qmt-rpyc-server status` | 报告进程状态，并区分 RPC 就绪与 QMT 连接状态 |

升级先确认安装方式及目标版本，再处理必要的停机和安装。完成输出应包含原版本、目标版本、安装验证结果、服务是否停止，以及保留配置路径的推荐启动命令。客户端提示重新启动使用该包的应用；跨 MINOR 升降级提示检查其他端及 BigQMT 策略的配套版本。

## 实现与验证范围

- 共用升级逻辑，覆盖默认稳定版、预发布、精确版本、降级、无版本变化、editable 拒绝、安装失败及新进程验证失败。
- 后台管理覆盖重复启动、单环境单实例、RPC 不可用时的本机管理、配置延续、请求与下载排空、超时恢复接收请求。
- 验证两个 update 入口均不会在安装后启动服务，服务端环境内的 client update 不绕过停机流程。
- 合并首次安装入口，删除冗余启动包装脚本，同步 README、仓库指南、发布工作流、验收包生成器和相关测试。
- 运行相关测试及完整可用的模拟测试；Windows 后台启动、控制台脱离和包替换行为需要 Windows 验证，报告时与本机模拟验证区分。

## Windows 升级执行

Windows console-script 启动器在运行时可能无法被 pip 替换，因此由独立 Python 辅助进程持有管理锁，等待原命令及其启动器退出后安装。命令先输出 `scheduled` 与日志路径，最终成功/失败和下一步命令写入该日志；`scheduled` 不表示安装成功。`python -m` 与 console-script 使用同一流程。

后台控制元数据及日志按当前用户和 Python 环境保存于系统状态目录。实例存活由操作系统文件锁判定，不凭 PID 杀进程；本机控制使用 loopback 上经随机凭据认证的有限 JSON 命令，独立于业务 RPC。元数据包含供显式重启使用的环境覆盖值，可能含敏感配置，不应上传或提交。
