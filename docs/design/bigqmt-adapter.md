# 完整 QMT 适配器设计讨论

状态：用户已选择 B，由本项目维护专用策略桥；完整实施方案仍在讨论。
架构决定见 [ADR 0003](../adr/0003-owned-bigqmt-strategy-bridge.md)。

## 目标与既有约束

参考 `xtquant_big_convert` 的实现，新增完整 QMT 适配器，接口范围与现有适配器一致。
以 `contracts/operations.py` 的 27 个公共操作及其请求、结果和行为约定为对齐基线，
通过 `adapters/interfaces.py` 的 Providers 接入现有服务。
保留原适配器，公共客户端不因来源替换而改变业务调用方式。
新适配器必须独立于原生 xtquant / XtQuantServer，仅依靠完整 QMT 的内置策略能力。
缺失能力继续调查、实机验证和补齐，不设置原生 SDK 回退。
下载是用户明确授权的例外：完整 QMT 自身管理数据获取，四类下载采用兼容空实现，
保留任务创建和状态查询；完成不表示桥接触发或确认了真实下载，详见
[ADR 0004](../adr/0004-bigqmt-compatibility-downloads.md)。
策略端须兼容目标终端的 64 位 Python 3.6.8；外部服务继续使用独立解释器，
策略不能直接加载要求较新 Python 的服务端包或公共 dataclass 模型。

实际支持能力以目标券商部署验证为准；参考源码和模拟测试不能替代 QMT 实机验证。
除明确约定的兼容下载外，不可通过伪造字段、成功结果或完成状态弥补来源差异。
调查阶段发现能力未知或不可用，不等于已完成接口范围对齐；如果实机确认存在无法补齐的能力，
应列出具体影响交由用户决定，不能自行缩减交付范围。

## 已核对的事实

- 当前 `adapters/registry.py` 提供显式适配选择，但仅注册 `xtquant_2.0.6.1`。
- 当前服务负责 RPC、业务调度与下载任务；适配器负责来源连接和数据转换。
- 参考项目把完整 QMT 的内置 Python 能力通过策略与跨进程通信提供给外部程序，
  并提供 MiniQMT 方法名兼容层。参见参考项目 `README.md`、
  `src/bigqmt_signal_trader_strategy.py` 的 `init`、`adjust` 和 `handlebar`。
- 参考项目 `pyproject.toml` 将顶层 `xtquant*` 一并打包，
  `src/xtquant/xtdata.py` 转发给 `bigqmt_signal_trader.xtquant_compat`。
  将该发行包直接安装到现有真实 SDK 环境存在命名空间冲突风险。
- 参考项目 `adapters/order_bigqmt.py` 的 `passorder_passthrough` 说明：
  `ContextInfo` 属于 QMT 内部上下文，其封装将下单作为异步提交处理。
  目标部署的 `passorder.__doc__` 声明返回 int，覆盖参考实现“返回 None”的假设；
  该整数是状态、请求号还是委托编号仍未验证。
  当前公共 `Submitted` 结果要求委托编号，因此必须另行验证可靠的订单关联与结果确认。
- 参考项目 `src/bigqmt_signal_trader/adapters/market_bigqmt.py` 中，
  `get_index_weight`、`download_index_weight`、`download_sector_data` 依赖原生 xtdata，
  没有纯完整 QMT 的回退实现。目标部署是否能通过其他内置 API 满足对应业务契约尚未知；
  不能把操作注册齐全等同于实际能力已对齐。

## 架构选择

### A：接入参考项目现有桥（未采用）

新增 Providers，调用参考项目的显式客户端，QMT 端部署其现有策略。
可复用较多已有功能，但需要隔离其顶层 xtquant 包，并审查兼容层的字段、
订单标识、重试及任务语义。后续运行和升级依赖两个项目的协议与版本。

### B：在本项目维护专用策略桥（已选定）

保留独立的 qmt-rpyc 服务进程，在新适配器内将业务请求交给本项目提供的 QMT 策略，
由策略执行内置 API；适配器返回现有公共模型。
参考已有的 QMT 调用、字段映射和线程约束，桥接范围限定为现有契约所需能力。
优点是公共语义与适配生命周期由本项目控制；代价是需要维护策略部署和内部通信，
并重新进行 QMT 实机验收。

通信方式已选择同机命名管道，策略线程执行内置调用，生产调度和打包方式仍待完成。

内部通信采用 Windows 同机命名管道：无需额外中间件，跨机器连接仍由现有 RPyC 提供。
目标策略环境已通过跨进程回显探针，包括大消息、慢读端、超时后新连接和停止清理，
但生产协议的并发、恢复及长期资源稳定性仍需验收。用户要求稳定可靠，具体要求见[可靠性设计](bigqmt-reliability.md)。
`run_time` 的一秒回调已实际执行且与 init 同线程；更短间隔及并发行为仍需验证，
不能把观测到的回调行为直接扩展为所有内置 API 的线程安全结论。

读取证据。板块全树遍历、完整指数权重单位和期权详情还需进一步验证，不能以少量样例代替验收。

## 阶段 3 实机结论

- `get_history_index_weight` 返回日期到历史成分代码列表，不含权重，不能用作权重接口。
- 期权公开样例含标的、到期日、行权价、合约单位和名称，保留 `.SHO` 后缀。
  认购认沽字段实际拼写为小写 `optType`；之前样例筛选误用 `OptType`，值域仍需补取。
- 日线返回代码到 DataFrame 的映射，日期索引与毫秒时间并存，字段含源端拼写
  `settelementPrice`。仅验证了无复权、两根日线样例，其余行为不据此推定。
- filled 财务入口返回按交易日索引的 179 行表，只有前两行被取样且均为 NaN。
  不能据此断言所有记录均为空。本地参考手册说明 filled 入口沿交易日填充，
  raw 入口才是逐报告记录的候选，需以目标部署实际结构为准。
- 期间出现“超出最大起始时间 20250928”的提示，指向时间范围限制；
  尚不能定位触发方法，也不把该日期作为永久业务边界。后续探针取消分钟线，
  并把财务查询限定为单字段、五天范围。

## 阶段 4 实机结论

- 小写 `optType` 的实测值为 `CALL`。合约允许的 `PUT` 暂由合成回归覆盖，
  不把该测试称为目标终端认沽样例验证。
- 五天单字段 filled 查询返回五行 DataFrame；输出只取样前两行，均为 NaN。
- 相同参数的 raw 查询默认返回 `code → 完整字段名 → dict`，该次最内层为空。
  已证实入口接受五参和外层结构，未证实非空记录的时间键、公告期/报告期关联及字段值。
- 本地参考手册和参考项目使用说明要求财务数据预先存在于终端，
  `ASHAREBALANCESHEET.tot_assets` 的表名、字段名有一致依据。
  这不证明目标部署自动下载失效，也不能凭空返回判断字段不支持。
  下一步先核对终端中一条可见的财务记录，按其已知日期取样；不继续更换猜测参数或扩大范围。

阶段 4 后续重跑已取得非空总资产记录；原始字段字典含一个整数毫秒时间键，
换算为上海日期是 `20260630`。相同代码和区间的 filled 样例也有值，
因此此前“只有空结构”的取证限制已解除。这不证明所有财务表都已准备好，
也不证明终端执行了哪种数据准备动作。下一阶段保持原窗口，核对双日期和各表字段；
尤其不能把 raw 时间键同时填入报告日和公告日。

JSON 桥协议必须保留原始财务时间键的整数类型，例如显式记录点或键值对数组；
不能通过普通 JSON 字典序列化把整数键悄悄改成字符串，也不能按日期键压平十大股东多行。
日期字段和同日多行结构取得实机证据前，不将该原始结构宣称为公共 FinancialReports。

## 阶段 5 实机结论及财报转换

五个标量表的双日期已实测：共同时间键对应报告期 `20260630`，
`m_timetag` 与 `m_anntime` 分别为报告期和公告日的浮点毫秒值，公告日换算为 `20260815`。
阶段 5 当时未证明 announce_time 的键结构；阶段 6 已补证，见下节。

股东户数是 DataFrame，含 stockCode、timetag、holdNum、AHoldNum、BHoldNum、HHoldNum、
uncirculatedHoldNum、circulatedHoldNum，未含公告日。
两类十大股东返回 Series，name 为日期、十个字段各自包含多值列表；
此前诊断只打印前三字段，已修正为输出最多四十个字段名与有界值样例。
后续阶段 6 已核对全部字段，仍缺十大股东公告日；不共用别表公告日。

`financial_wire.py` 已实现 Python 3.6 可用的标量字段编码：整数时间键通过显式键值对数组
跨越严格 JSON，NaN 规范化为 null，省略点保留省略语义，多行股东结构不得误用该编码压平。
`financials.py` 已实现标量表到公共记录的转换：按相同源时间键关联字段，保留双日期，
转换时使用上海时区，拒绝重复键、日期缺失、孤立数值以及日期基准错配。
这些模块仍未装配到生产策略桥。

此前把可空指标缺失也当作接口阻塞过于严格。现有契约明确财务数值缺失时为 null，
因此 EPS、期末现金等来源缺值按该约定表达，不补造数值，也不影响真实报告及日期的返回。
阶段 6 已证明这些候选数值字段有值；缺值时的 null 规则继续适用。
公共双日期是必需字段，缺失仍无法返回合法记录。
本地参考文档明确自由流通股本新名 free_float_capital 的旧名是 freeFloatCapital，
结合目标字段实测已实现该别名映射，无需再增加别名探针。

用户已确认有模拟账户可用于后续交易验证。已准备[模拟账户只读探针](bigqmt-trading-probe.md)，
先核对资产、持仓、委托原始字段与身份关系，账号仅在终端本地填写。
账户可用不等于已验证下单或撤单；后续仍需核对实际返回值、回调与订单关联。

## 阶段 7：十大股东默认 raw 无法表达全部行

两个原始表均返回同一期一条记录，rank 为 10，含真实双日期与数值；
日志明确未截断。与专用入口的十条股东列表相比，默认 raw 字典不足以实现完整公共表。

不推测数据丢失发生在原生查询还是字典构造阶段，也不将单行公告日广播给所有股东。

## 最新范围调整：仅保留五张核心财务表

阶段 8 加上 frame 参数后仍返回同一字典和末位股东，无法提供完整列表。

因此停止股东调查，不再把 HolderNum、Top10Holder、Top10FlowHolder 作为新 adapter 的验收条件。
保留 Balance、Income、CashFlow、Capital、PershareIndex 的既有关键字段与真实双日期。

默认财务查询和下载请求改选五表；用户随后授权统一删除股东接口，当前公共契约只保留五表。
新 FinancialsAdapter 通过专用 reader 获取原始字段的 JSON 编码，按输入顺序返回逐项结果，
区分空报告、缺失结果、数据错误和桥不可达；股东请求在公共参数校验阶段即失败，适用于所有 adapter。
HolderNum 转换及三种股东记录模型已删除；历史探针只留作调查记录，不再运行。
生产策略桥的装配仍未完成，不能将单元测试通过视为端到端上线。

用户已确认模拟配置尚未修改或被覆盖，最新配置失败不属于 QMT API 故障，
仍未产生探针订单；后续只需在终端本地填写并保存，无需继续调查配置校验本身。
